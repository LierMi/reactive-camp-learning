# 读懂费用：用 cast 查询 Lasna 系统合约参数

- 查询日期：2026-11-25（UTC）
- 网络：Reactive Lasna 测试网（Chain ID `5318007`）
- RPC：`https://lasna-rpc.rnk.dev/`
- 系统合约：`0x8888888888888888888888888888888888888888`

## 先弄懂这道题在看什么

普通合约通常是有人发交易才执行。Reactive 合约可以**订阅事件**：某条链上的合约发出符合条件的日志后，Reactive 网络会把这条日志交给 Lasna 上的系统合约，系统合约再调用我们的 `react()`。`react()` 可以做判断，也可以请求在另一条链上执行回调。学习营 starter 展示的就是“源链发事件 → Lasna 执行 `react()` → 目标链收到回调”这条路线。

这道题只研究中间一步的**收费规则**，不用部署合约，也不用发送交易。我们读取的是 Lasna 系统合约保存的三个配置值。它们是计费规则的参数，**不是某一笔 `react()` 的实际费用**。

几个容易混淆的词：

| 词 | 新手理解 |
| --- | --- |
| Lasna | Reactive 的测试网；本题的查询发生在这条链上。 |
| 系统合约 | 网络用于订阅、触发 `react()` 和结算费用的合约；本题查询它的地址是 `0x8888…8888`。 |
| RPC | 让命令行工具向区块链节点提问的接口；这里的地址是 `https://lasna-rpc.rnk.dev/`。 |
| gas | 衡量一次链上计算用了多少资源的单位。gas **用量**和每单位 gas 的**价格**是两个不同的数。 |
| `react()` | Reactive 合约收到匹配事件时由系统合约调用的函数。 |

## 我是怎么做的

`cast` 是 Foundry 的命令行工具。这里用 `cast call` 读取合约状态，属于只读查询，不用钱包、私钥或测试币。命令末尾的 `cast to-dec` 把合约返回的十六进制数转成十进制，方便看数值。

第一次操作可以这样做：打开 macOS 的“终端”，输入 `cast --version` 并按回车，确认 Foundry 已安装；然后逐条复制下面 `$` 后面的命令并按回车。`$` 只是表示终端提示符，下一行的数字是输出，**不要把 `$` 和输出数字一起粘贴到终端**。

以第一条命令为例：`cast call` 表示只读查询；后面的长地址指定“问哪个合约”；`'_gasPriceCoeffPer1000()'` 指定“问合约里的哪个函数”，空括号表示没有输入参数；`--rpc-url` 指定连接 Lasna；`|` 把前一条命令的输出交给 `cast to-dec` 转成十进制。与 `cast send` 不同，`cast call` 不会发起需要付费的链上交易。

在终端依次运行以下三条命令，我得到：

```bash
$ cast call 0x8888888888888888888888888888888888888888 '_gasPriceCoeffPer1000()' --rpc-url https://lasna-rpc.rnk.dev/ | cast to-dec
1000

$ cast call 0x8888888888888888888888888888888888888888 '_extraGas()' --rpc-url https://lasna-rpc.rnk.dev/ | cast to-dec
100000

$ cast call 0x8888888888888888888888888888888888888888 '_maxChargeGas()' --rpc-url https://lasna-rpc.rnk.dev/ | cast to-dec
50000
```

这三个参数可由系统合约所有者调整，因此上面是查询当时的值，以后使用时应重新读取。

## 1. 一次 `react()` 的费用怎么算？

我理解为：先取基础 gas 价格，再乘价格系数，最后乘“这次执行实际用掉的 gas + 固定附加 gas”。公式是：

```text
费用 = 基础 gas 价格 × (_gasPriceCoeffPer1000 / 1000) × (实际消耗 gas + _extraGas)
```

基础 gas 价格取 `tx.gasprice` 与 `block.basefee` 中较大的那个。今天查到的系数 `1000 / 1000 = 1`，固定附加 gas 是 `100000`。因此按当前参数，公式可以写成 `费用 = 基础 gas 价格 × (实际消耗 gas + 100000)`。

`_gasPriceCoeffPer1000` 的名字可以读成“以千分之一为单位的价格系数”：读到 `1000`，要先除以 `1000`，得到 `1` 倍；不能直接把费用乘以 `1000`。`_extraGas` 是每次计费额外加上的 gas **数量**，不是另一个 gas 价格，也不表示 `react()` 真的多执行了 100,000 gas 的代码。

例如，**仅作算例**：若实际消耗 `60000 gas`，基础 gas 价格为 `100 gwei`，费用就是 `100 gwei × (60000 + 100000) = 0.016 REACT`。这里的 gas 价格和实际用量是举例，不是这次查询得到的实时值。

单位换算也可以自己验算：`1 gwei = 10^9 wei`，`1 REACT = 10^18 wei`，所以 `100 × 160000 × 10^9 ÷ 10^18 = 0.016 REACT`。**这三条 `cast call` 只能查到参数，查不到算例中的实际 gas 用量或 gas 价格。**

`_maxChargeGas = 50000` **不加进这个公式**。它是系统合约在需要调用付款逻辑 `pay()` 时，给这一步设置的 gas 上限，也不是 `react()` 的执行 gas 上限。

## 2. `balance`、`reserves`、`debt` 是什么？为什么一点 debt 也会停？

| 名称 | 我理解的意思 |
| --- | --- |
| `balance` | Reactive 合约自身持有的 REACT，可以用来付款。 |
| `reserves` | 存在系统合约里、专门为这个 Reactive 合约预付费用的资金。收费时先扣它。 |
| `debt` | 系统合约记录的未付费用。 |

可以把它们想成三个不同的记账位置。假设本次费用是 `0.016 REACT`：若 `reserves` 原有 `0.020 REACT`，结算后剩 `0.004 REACT`；若预付金不足，系统合约会尝试调用合约的 `pay()`，用它自己的 `balance` 结清欠款；如果余额不足、付款失败，未付部分就留在 `debt`。这只是说明结算顺序的例子，并非查询某个真实合约的余额。

系统合约在调用 `react()` **之前**先检查 `debt`。只要 `debt > 0`，它就不会继续调用这个合约的 `react()`；规则没有“欠得少就通融”的阈值。这避免继续为尚未结清费用的合约提供执行服务。

直接给合约转 REACT 只会增加它的 `balance`，不会自动清除已经存在的 `debt`。要恢复执行，可以向系统合约调用 `depositTo(合约地址)`，它会先还债，再把剩余资金记入 `reserves`；如果合约自己公开了 `coverDebt()`，也可以用合约余额主动还债。

## 3. `react()` 回滚了，还收费吗？对设计有什么影响？

**还收费。** 系统合约会捕获 `react()` 的回滚、记录失败事件，然后仍按已经消耗的 gas 计费。一次失败的执行也占用了网络计算资源，所以不能把 `revert` 当作免费的事件过滤器。

这里的“回滚”是指 `react()` 的状态修改没有成功留下来；它不等于这次尝试没有发生。`return` 是正常结束函数，`revert` 是宣告执行失败。两者都可能消耗 gas，但如果只是发现事件不符合业务条件，尽早 `return` 通常更合适，也避免不断记录失败。

写合约时，我会尽量把订阅条件设准；在 `react()` 里遇到无需处理的事件，做判断后尽早 `return`，而不是 `revert`。还要在本地测试可能失败的路径，并留意资金和 `debt`：如果错误反复触发，失败费用会持续消耗资金，最终让合约停止响应。
